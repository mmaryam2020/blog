The secret to a great personal AI bot? Simple architecture. 🛠️🤖

When I set out to build my ultimate personal AI assistant, I evaluated several complex frameworks. I ultimately built upon the NanoClaw v1 orchestrator because of its brilliant architectural simplicity:

  • 📦 Docker Isolation: The Claude SDK runs in a sandboxed container.
  • 📂 File-Based IPC: Host and container communicate simply by dropping JSON files into a shared folder. No complex WebSockets.
  • 🗄️ SQLite: Single-file persistence.

Because it’s so beautifully simple, I’ve been able to easily fork it and bolt on custom features like Strava MCP integration, Vercel web-publishing, and reliability guards for cron tasks.

I realized this architecture is perfect for anyone wanting to build their own personal bot, so I put together this interactive Wiki to break down exactly how it works under the hood.

🏗️ Core Architecture

NanoClaw operates as a single-process Node.js orchestrator designed to handle fully isolated agent runs inside containers.

⚡ Execution Lifecycle

Message Inbound Flow

  1. Inbound Adapter captures message events.
  2. onMessage() inserts message into local database.
  3. src/index.ts loop detects unread database entries.
  4. Active triggers process gating rules.
  5. GroupQueue fires up or routes to an active container.

Scheduled Task Flow

  1. src/task-scheduler.ts scans the scheduled_tasks list.
  2. The target task is queued in the group's container queue.
  3. The container runs in specialized context_mode.

🔒 Isolation & IPC

Complete host-to-agent safety is established using isolated Docker sandboxes, coordinating using file-based IPC.

  • Safe Mounts: Maps groups/{name} straight into /workspace/group.
  • IPC Path: Orchestrated via data/ipc/{group}/:
    • messages/: Pending agent requests.
    • tasks/: Schema and task changes.
    • input/: Direct console piping.
  • Mount Gating: src/mount-security.ts validates all directory inclusions.

💾 Data Model (SQLite)

Crucial persistent schema tables defined under src/db.ts:

  • chats: Tracks communication channels and groups.
  • messages: Retains long-term dialogue exchange logs.
  • scheduled_tasks: The persistent source of truth for scheduled cron runs.
  • sessions: Tracks active LLM conversations.
  • router_state: Keeps tabs on channel event cursors.

⚠️ Critical Architecture Rules

  • Asynchronous Polling: The orchestrator uses recursive setTimeout loops (rather than blocking or fixed intervals) for IPC and database synchronization to ensure the event loop remains clear.
  • 1GB Hard Limits: Ensure at least 1GB memory allocation per container to avoid OOM crash code 137.
  • Concurrency Control: GroupQueue serializes commands to guard the single-container invariant.
  • Privilege Escapes: Main group instances are granted global directory write privileges and full folder inclusions.
