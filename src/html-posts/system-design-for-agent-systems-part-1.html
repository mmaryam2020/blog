System Design for Agent Systems (Part 1)

A conceptual mental model for the engineering outside the LLM: why agent workloads break web service assumptions, how to structure state, and how to evaluate non-deterministic systems.

💡 The Central Thesis
“Put a frontier model into a badly designed agent system and you get a more articulate failure. Nearly all of the engineering sits outside the model, in the scaffolding called the agent harness.”

Swapping the model does not fix architectural bugs. The scaffolding—tool contracts, prompt cache ordering, memory boundaries, unidirectional orchestration, and evaluation gates—remains 100% unchanged regardless of which frontier model you use.

Workloads

“Whoa there! Agent jobs take minutes, not milliseconds. Do not hold open synchronous HTTP connections or you will time out! Always size workers for async I/O wait, not CPU cores.”

Idea 1 The Mental Model Shift: Agent Jobs ≠ Web Requests

Most failures in agent systems occur because engineers apply standard web service design patterns to agent runtimes. Their resource profiles are polar opposites:

Dimension Traditional Web Workload Agent Workload
Latency 50–200ms synchronous bursts Minutes per job (must be asynchronous)
Bottleneck CPU & memory bound 70–80% I/O wait on LLM provider APIs
Determinism Deterministic (assert in CI) Non-deterministic (retries are not free)
Marginal Cost Near zero ($0.00001 / request) A bug is a bill (~$1/min in a silent infinite loop)
The Key Takeaway: Never hold synchronous HTTP connections open. Design for asynchronous I/O and enforce external spend budgets because runaway loops do not crash—they silently burn dollars.
Idea 2 Tool Design as a Contract
1. Small Surface Area & Strict Typing

Expose small, single-action tools with rigid schemas rather than kitchen-sink functions. Ambiguous parameters confuse the model and waste context tokens on erroneous tool calls.

2. Timeouts & Centralized Logging

Register tools centrally and assign every tool a mandatory execution timeout. Log all inputs, outputs, and latencies to prevent hung processes and simplify debugging.

Idea 3 State & Prompt Caching Rules
1. Static Content Precedes Dynamic Data

Place static instructions and schemas before dynamic conversation history and retrieval chunks. Injecting dynamic variables near the prompt head invalidates KV caching and doubles token bills.

2. Decouple Working and Persistent Memory

Working memory holds immediate conversational context, while persistent storage tracks long-term facts across sessions. Re-injecting historical state into system prompts wastes tokens; seed working memory once at startup.

Idea 4 Control Topology & Stop Budgets
1. Sequential Subagents Beat Parallel Chaos

Sequential subagents establish deterministic data flow and enable early exits when early steps fail. Parallel coordination causes race conditions, complex merging overhead, and unnecessary token spend.

2. The 4 Enforced Stop Ceilings

The model's completion signal is its least reliable exit. The harness must independently enforce hard ceilings on tool steps, wall-clock duration, and dollar budget.

3. Loop Engineering vs. Graph Engineering

Start with a single agent loop. Move decisions into a rigid graph topology only when failure must be physically impossible rather than merely unlikely.

Idea 5 Human Gates & The Evaluation Pyramid
1. Gate on Irreversibility, Never Importance

Gate actions mechanically based on whether another tool can undo them. Reads and drafts are reversible, while publishing or deleting are not; gating everything causes approval fatigue.

2. The Three-Tier Evaluation Pyramid

Unit test harness state transitions deterministically in CI without model calls. Evaluate non-deterministic outputs via sampling rubrics and periodic LLM-as-a-judge regression tests.
